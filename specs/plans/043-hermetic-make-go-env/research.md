# Phase 0 Research: a hermetic `make` Go-toolchain environment (Round 043)

Topic: give the `Makefile` a single **hermetic invocation boundary** so every Go-toolchain invocation `make` launches runs with a sanitised, explicit environment — neutralising the build-context inputs an ambient or persisted Go env can inject (`GOENV` file, `GOFLAGS`, `GO111MODULE`, `GOWORK`, ambient `GOOS`/`GOARCH`) while preserving the warm-cache and network/checksum inputs a cold-cache or proxied build needs — resolving issue [#96](https://github.com/gosharplite/tellme/issues/96) (the **outer** half of round-042's **F-2**).

Scope note: the language (`Go 1.26`), module, CLI flag layer, config layer, testing harness, provider transports, skills, MCP, presentation, and build gates were locked in rounds 001–042. The round adds **no new system end**, **no external service**, and **no new third-party dependency**. The three AIxBDD must-ask questions are answered by the standing `techstack.md` (single CLI end; BDD techstack = `godog` on the built binary; E2E + unit strategy) and are **not re-decided** (D12). **IN**: the `Makefile` boundary, ADR 0012, the truth rows, and the falsifiability/positive-control witnesses. **OUT**: any product code, any bare-`go`-outside-`make` hermeticity, and any existing gate's semantics.

> **Lineage:** this generalises round-042's `tools/arch` `childEnv` (ADR 0011 **D5**) from the gate's own child `go list` to **every** target; round-020's `verify-cross-compile` `CGO_ENABLED=0` pin (PR #46 **TD1**) is the **precedent** — generalised here as an **invocation** rule; the pin itself stays **recipe-local** (D4). Origin: PR [#95](https://github.com/gosharplite/tellme/pull/95) fold-review #2 (comment `5721537481`, Fold 2).

## Decision 1: Mechanism — one top-of-`Makefile` `export`/`unexport` block (clarify Q2 → A1)

- **Decision**: define the hermetic environment **once**, near the top of the `Makefile` (above the `$(shell command -v …)` toolchain probes and before any recipe), using GNU-make `export`/`unexport`: `export GOENV := off`, `export GOWORK := off`, and `unexport GOFLAGS GO111MODULE GOEXPERIMENT GOOS GOARCH GOARM` (the precise list is D2). Every recipe — and every nested `go` invocation a scripted recipe spawns — inherits it.
- **Rationale**: the failure class is **repo-wide**, so a single owned definition is the only form that does not drift. A1 also covers the **descendant** `go build` that `make test` (via the E2E harness) and `verify-no-network` spawn — which per-recipe `$(HERMETIC_ENV)` prefixes (A2) would **miss**, because those spawns happen inside a shell script, not on a recipe line. A new target added later is hermetic **by construction**.
- **Scope of the boundary (TD-1, reproduced; corrected by PR #99 review N-1):** `export`/`unexport` govern **recipe** environments (and their descendants) **only** — **not** parse-time expansion. A `$(shell …)`/`$(eval …)` child receives make's **original environment verbatim**: a makefile `export` does **not** reach it and `unexport` does **not** strip it (measured, GNU Make 4.3, block in place: ambient `GOENV=<file> GOFLAGS=-mod=vendor GOTOOLCHAIN=go1.99.9` ⇒ recipe `GOENV=[off] GOFLAGS=[] GOTOOLCHAIN=[]`, parse-time `GOENV=[<file>] GOFLAGS=[-mod=vendor] GOTOOLCHAIN=[go1.99.9]`). A **command-line** `VAR=…` is not exported to recipes (`make GOFLAGS=-mod=vendor vet` ⇒ neutralised) but **overrides** an already-`export`ed name (`make GOENV=<file> vet` ⇒ the file wins). **Consequence:** keep `go` out of `$(shell …)` — parse-time escapes the boundary for **every** name; the parse-time/command-line surface is a recorded residual (R5). The repo-wide scope figure is **25 `grep` lines / 16 executed toolchain invocations** (R-3; `verify-cross-compile`'s single line carries two).
- **Alternatives considered**:
  - **A2 — an explicit `$(HERMETIC_ENV)` prefix per invocation** — ~16 executed invocation sites (25 `grep` lines), a new recipe silently misses it, and it does not reach descendant spawns — rejected.
  - **A3 — both** — redundant once A1 covers nested spawns; more surfaces to keep in sync — rejected.
- **Note on `make VAR=…` overrides**: a contributor who deliberately wants an ambient setting can export it explicitly for the invocation (`GOPROXY=… make verify`) — the documented escape hatch (D8).

## Decision 2: The neutralise set (criterion-derived), the preserve set, and the `CGO_ENABLED` stance (clarify Q3 → V1; B-4)

- **Decision — the inclusion criterion** (the rule for adjudicating the *next* name; PR #97 review **B-4**):
  > **Neutralise the ambient *build context*** — anything that changes **what** the Go toolchain builds or **which** toolchain builds it (module mode · build flags · workspace · experiments · target triple incl. the micro-architecture level · toolchain selection · build-mode/runtime switches). **Preserve the *plumbing*** — the warm cache/runtime roots and the network/checksum configuration.
  - **Neutralise/replace** — `GOENV` → `off`; `GOWORK` → `off`; `GOFLAGS`, `GO111MODULE`, `GOEXPERIMENT`, `GOTOOLCHAIN`, `GOFIPS140`, `GODEBUG` → **unset**; the target triple: `GOOS`, `GOARCH` **and** the micro-arch family `GOARM`, `GOARM64`, `GOAMD64`, `GO386`, `GOMIPS`, `GOMIPS64`, `GOPPC64`, `GORISCV64`, `GOWASM` → **unset** (host-native).
  - **Preserve** — `PATH`, `HOME`, `GOPATH`, `GOMODCACHE`, `GOCACHE` (warm-cache set) **and** `GOPROXY`, `GOSUMDB`, `GOPRIVATE`, `GONOSUMDB`, `GOINSECURE` (network/checksum set).
  - **`CGO_ENABLED`** — **preserved from the caller** (neither set nor unset; not globally pinned) — R-1(1) wording fix; the only cgo pin remains `verify-cross-compile`'s inline `CGO_ENABLED=0` for its own recipe.
- **Rationale**: the sets mirror round-042's `childEnv` discipline, extended to the preserve set the parent invocation needs. Preserving `GOPROXY`/`GOSUMDB`/… is essential: with a **cold** module cache (or behind a corporate proxy) the aggregate must still resolve modules; an `env -i`-style wipe would fail with a cache/resolution error (the `verify-cross-compile` **PR #46 TD1** lesson, in the parent). The **criterion** (not an incident list) is what makes the set auditable: `GOTOOLCHAIN` was reproduced red (`GOTOOLCHAIN=go1.99.9 make vet` ⇒ **exit 2** *toolchain not available*) and the micro-arch family is squarely "target triple", so both are in-class; "host-native" for an unset `GOOS`/`GOARCH` covers the OS/arch **pair only**.
- **Alternatives considered**:
  - **V2 — also pin `CGO_ENABLED=0` globally** — a **real behaviour change**: it would exclude any future cgo-tagged code (the recorded darwin `mach` CPU sampler is exactly such a candidate) from `make build`/`make test`, and diverge from a plain `go build`. Violates #96's own "no gate's behaviour changes for a clean environment" criterion — rejected.
  - **V3 — neutralise only the module/work vars; leave `GOOS`/`GOARCH`/`CGO_ENABLED` ambient** — a stale exported `GOOS=linux` on a macOS dev box would still miscolour `make build`/`test` (same family as the issue) — rejected.
  - **An incident-derived 8-name set** (the first draft) — not auditable (why is `GOTOOLCHAIN` out and `GOARM` in?); rejected per B-4.

## Decision 3: Scope — unconditional, all targets (clarify Q4 → S1)

- **Decision**: the block applies to **every** target — `build`, `fmt`, `vet`, `tidy`, `test`, `lint`, `staticcheck`, `vulncheck`, every `verify-*`, and `verify`. No per-target opt-out.
- **Rationale**: A1 is unconditional by nature; scoping it to a gate-family subset (S2) would require *undoing* it per target (re-exporting ambient values), reintroducing exactly the per-site drift A1 removes. And a target added later is hermetic by construction.
- **Verification folded for the widest surface (Q7-R2)**: `fmt`/`tidy` are **mutating** targets; a **positive control** (D7) confirms the block does not break them (`gofmt`/`go fmt` use no build flags; `go mod tidy` still resolves via the preserved `GOPROXY`/`GOSUMDB`/… and leaves `go.mod`/`go.sum` unchanged in a clean env).
- **Alternatives considered**: **S2 — gate/test family only** (leaves `build`/`fmt`/`tidy` ambient) — fights A1 and silently ambient-ises future targets — rejected; **S3 — S1 + an explicit `HERMETIC=0` opt-out** — a reasonable add-on, recorded as a forward option, not needed for this round.

## Decision 4: `GOENV=off` is load-bearing (not decoration)

- **Decision**: the block sets `GOENV=off`, **and** this is documented as the mechanism that makes the whole thing work.
- **Rationale**: Go resolves a variable from the **env file** whenever it is **unset or empty** in the process environment, so simply deleting or emptying `GOFLAGS` does **not** neutralise a persisted `go env -w GOFLAGS=-mod=vendor` — the exact failing case in [#96](https://github.com/gosharplite/tellme/issues/96). Round-042 review **F-2** established this for the child `go list`; this round elevates it to the parent. `GOENV=off` is the documented Go value that disables the env-file fallback entirely.
- **Alternatives considered**: **unset `GOFLAGS` only** — defeated by the env file for the persisted case (would leave the issue's headline reproduction red) — rejected.

## Decision 5: Round-042's `childEnv` is retained as defence-in-depth; primary owner is the `Makefile` (clarify Q6 → D1; PR #97 review B-2/B-3)

- **Decision**: keep `tools/arch/arch_test.go`'s `childEnv` filter in place; add a short cross-reference **comment** in both the `Makefile` block and the guard, naming the `Makefile` block as the **primary owner** and `childEnv` as the cover for the gate's **verdict** on the **direct** invocation of the gate. The invariant between the two sites is **coverage**, **not equality**: *every name in D2's neutralise set is either re-set explicitly by `childEnv` or recorded as a non-covered class (D8/R4)* — R4's list is exact and closed (14 names).
- **Rationale**: the gate is documented (`tools/arch/doc.go`, the baseline header, the `techstack.md` row) as runnable **directly** (`go test -count=1 -tags=arch -run TestVerifyRealArchitecture ./tools/arch`), which bypasses `make`. On that path `childEnv` keeps the gate's **own child `go list`** hermetic — the **verdict** — while the direct path's **outer** `go test`/`go vet` remain **non-hermetic** (an ambient `GOENV=<file>` still reaches them; reproduced: exit 1 — review **B-2**). That is R1, not a claim `childEnv` does not make. Deleting `childEnv` would regress that documented path's verdict and reopen frozen round-042 history.
- **Why equality is the wrong invariant (review B-3)**: the two sites neutralise by **different mechanisms** — the `Makefile` **disables the env file** (`GOENV=off`) and unsets; `childEnv` **re-sets explicit non-empty values** (`GOOS`/`GOARCH` per target, `CGO_ENABLED=0`, `GOFLAGS=-mod=readonly`, `GO111MODULE=on`, `GOWORK=off`) that win over the file (round-042 **F-2**). The **literal** symmetric difference is **12 Makefile-only names** + `{CGO_ENABLED}` on the `childEnv` side; **semantically** the **non-covered set is 14** (PR #99 review **N-4**) — `GOEXPERIMENT` and `GOARM` sit in **both** literal sets because the filter *drops* them, but `childEnv` never *re-sets* them, and by the round's own F-2 doctrine **drop ≠ neutralise** (Go falls back to the env file). So on the direct path an **env-file**-supplied value for those still reaches the gate's child `go list`. Round 042 is **frozen** → **recorded** (D8/**R4**, whose list is exact and closed), not fixed.
- **No "drift witness"**: an assertion that the two literal sets **agree** would fail by design, and a non-committed grep is not a witness (it cannot fail on its own). The coverage invariant is recorded as a **maintenance invariant** in ADR D6; the implementation's check asserts the **coverage direction** (it excludes `CGO_ENABLED`, the documented mechanism difference), not equality.
- **Alternatives considered**:
  - **D2 — delete `childEnv`, single owner** — loses the direct path's verdict hermeticity and reopens frozen artifacts — rejected.
  - **D3 — a shared definition the `Makefile` sources** — awkward make↔Go coupling disproportionate to a handful of literals — rejected.
  - **A drift witness asserting the two sets agree** — false by design (different mechanisms); the coverage invariant replaces it — rejected (review B-3).

## Decision 7: Verification — four red→green witnesses + the neutralisation assertions + two positive controls

- **Decision**: the acceptance evidence is (a) **four red→green hostile-env witnesses** — `GOENV=<file: GOFLAGS=-mod=vendor>`, `GO111MODULE=off`, a stray `GOWORK=<path>`, `GOTOOLCHAIN=go1.99.9` — each asserted **red before** the change and **green after** (reproduced then reverted, ADR 0010 doctrine; **a witness must be able to fail** — review **B-1**); plus the **neutralisation assertions** for green-before inputs (`GOFLAGS=-trimpath` and the long-tail D2 names are asserted **absent from the recipe environment** — a `make`-level probe — and are **not** counted as witnesses); plus the **aggregate-level evidence** (`GOENV=<file: GOFLAGS=-mod=vendor> make verify` ⇒ **exit 0** with every member green — stronger than one target); and (b) **two positive controls**:
  - **cross-compile**: `make verify-cross-compile` still builds + vets **4/4** targets under the hermetic env — proving the block neutralises *ambient* env **without** clobbering a recipe's intentional inline per-target `GOOS`/`GOARCH`/`CGO_ENABLED=0` (FR-012);
  - **mutating targets**: under a **clean** env, `make tidy` and `make fmt` leave `go.mod`/`go.sum` unchanged and produce no source diff (Q7-R2).
  - The `childEnv`↔`Makefile` relation is checked as the **coverage direction** (D5), not an equality "drift witness".
- **Rationale**: the two "positive controls" are what separate a *hermetic* change from a *destructive* one — they prove we removed only the ambient inputs and kept the intentional ones and the mutating targets working. The B-1 distinction (witness vs assertion) is ADR 0010's falsifiability test applied to the plan's own evidence list.
- **Alternatives considered**: **rely on `make verify` green alone** — does not exercise the failing inputs (vacuous) — rejected; **count `GOFLAGS=-trimpath` as a witness** — green before the change, so it cannot fail (review **B-1**) — rejected; **an E2E Gherkin carrier** — no user-facing CLI behaviour to express (D9) — rejected.

## Decision 8: Recorded residuals (clarify Q7 → R1 + R3; PR #97 review → R4 + R5)

- **Decision**: record four residuals in ADR 0012's Consequences and the truth row:
  - **R1** — a bare `go test ./...` / `go build` **without `make`** stays non-hermetic (hermeticity is a **`make`-boundary** property, not a toolchain property), **including the gate's documented direct invocation's outer `go test`/`go vet`** (D5/B-2).
  - **R3** — the escape hatch is **per variable class**: an already-`export`ed name (`GOENV`, `GOWORK`) via a command-line assignment (`make GOENV=<file> verify` — it re-injects a whole env **file**); a plumbing name via an explicit export (`GOPROXY=… make verify`); the **unexported** names (`GOFLAGS`, `GO111MODULE`, `GOEXPERIMENT`, `GOTOOLCHAIN`, the target-triple family, `GOFIPS140`, `GODEBUG`) have **no in-make hatch** — invoke the toolchain directly or edit the block.
  - **R4** — inside the **frozen** round-042 guard, `childEnv` **drops but does not re-set** the **14** non-covered names (ADR 0012 R4): `GOENV`, `GOEXPERIMENT`, `GOTOOLCHAIN`, `GOFIPS140`, `GODEBUG` + the micro-arch family `GOARM`/`GOARM64`/`GOAMD64`/`GO386`/`GOMIPS`/`GOMIPS64`/`GOPPC64`/`GORISCV64`/`GOWASM`. On the direct path an **env-file**-supplied value for those still reaches the gate's child `go list` (the round-042 F-2 shape *inside* the guard). Recorded, not fixed (round 042 is frozen); a future round may extend `childEnv` by citation.
  - **R5** — the boundary governs recipes + descendants; **parse-time `$(shell …)`/`$(eval …)`/`include`d-makefile/command-line variables are outside it** (D1/TD-1): keep `go` out of `$(shell …)`. A future Go env name outside the D2 criterion's categories is out of scope until added (the criterion is the rule for deciding).
- **Rationale**: R1 bounds the claim honestly (an "all Go invocations are hermetic" claim would be false); R3 documents the accepted cost of the mechanism required to fix the persisted case (D4) with a concrete per-class hatch; R4 records that the two mechanisms are complementary rather than duplicates (B-3); R5 records the boundary's edge (TD-1); R6 records the **make-level** inputs that resurrect the two `export`ed names — `-e` mode (`make -e` / ambient `MAKEFLAGS=-e`) reproduced at the PR #99 review **N-5** (`GOENV=<file> … make -e vet` ⇒ exit 2; the 17 `unexport`ed names unaffected), plus the contrived `MAKEFILES`-injected `override export` (PR #99 review **N-6**: an `override export GOFLAGS=…` so injected is still defeated by the `unexport`, and `MAKEOVERRIDES` has no channel — no `$(MAKE)` recursion) — recorded rather than closed because closing costs the R3 hatch or adds a failure mode.
- **Alternatives considered**: **preserve `GOENV` and only neutralise `GOFLAGS`** — leaves the persisted case red (D4) — rejected; **silently presume `childEnv` covers the D2 names** — false for `GOARM`/`GOEXPERIMENT` + the new names (R4) — rejected.

## Residual risks / forward links

- **Bare `go` outside `make`** stays non-hermetic (D8/R1) — recorded; a global shim is out of scope. This includes the gate's documented direct invocation's **outer** `go test`/`go vet` (D5/B-2); `childEnv` keeps its **verdict** hermetic.
- **`GOENV=off` vs a legitimate env-file setting** (D8/R3) — the escape hatch is **per variable class** (a command-line `make GOENV=<file>`; an explicit plumbing export; direct invocation for the unexported names).
- **Two *mechanisms*, one *coverage* invariant** (`Makefile` block + `tools/arch` `childEnv`, D5) — complementary, not duplicates; cross-reference comments both ways; the non-re-set names on the direct path are R4 (recorded, not fixed inside frozen round 042).
- **Parse-time / command-line surface** (D8/R5) — `$(shell …)`/`$(eval …)`/`include`d makefiles/command-line variables are outside the boundary; **keep `go` out of `$(shell …)`**.
- **A future recipe that *wants* an ambient build flag** — an explicit export or a direct invocation is the hatch; the block owns the ambient default.
- **`CGO_ENABLED` on a cgo-less host** — an ambient `CGO_ENABLED=1` without a C compiler still breaks a *non-cross* `make build`; that is **not** one of #96's cases (the issue scopes `GOFLAGS`/`GOENV`/`GO111MODULE`/`GOWORK`), and pinning `0` globally is the rejected V2 — recorded.
- **`make help` `verify-no-network` text** — a pre-existing stale-help item (round-032 R8d), unrelated; not touched here.
- **No behaviour change** — `stdout`/`stderr`, the class-phrase vocabulary, flags, exit codes, every existing gate's semantics, and `internal/**`/`cmd/**`/`tests/**` are unchanged; the round touches the `Makefile`, `docs/decisions/**`, and `specs/truth/techstack.md`.
